ТЗ: исправление архитектуры отображения политического слоя на SVG-карте

1. Контекст проекта

Есть веб-приложение для интерактивной DnD-карты мира.
Карта реализована на основе SVG (world-map.svg), поверх которого работают:
- выбор провинций;
- режимы master / player;
- отображение персонажей;
- отображение маркеров;
- масштабирование через изменение viewBox;
- редактирование данных по провинциям, персонажам и маркерам.

Текущее состояние логики находится в dnd-map-mvp/app.js.
Сейчас базовый zoom уже ограничен стартовой рамкой: state.zoom.min = 1, а масштаб меняется через viewBox SVG.

2. Проблема

Сейчас политический слой реализован неправильно: приложение напрямую изменяет стили исходных SVG-элементов карты.

Это видно в текущей логике:
- есть getProvinceElement(provinceId);
- есть getProvinceGapElement(provinceId);
- функция applyProvinceStyles() напрямую меняет fill, fill-opacity, stroke, stroke-width у исходных state* и state-gap* элементов через setProvinceVisualStyle().

Симптомы:
- при увеличении масштаба цветной слой визуально ведёт себя нестабильно;
- заливка выглядит так, будто смещается относительно карты;
- складывается ощущение, что цвет тянется не к центру, а к правому верхнему углу;
- цветной слой живёт отдельно от базовой геометрии карты.

Предполагаемая причина:
Проблема не в самом zoom, а в том, что:
- исходный SVG используется одновременно и как художественная подложка, и как динамически перекрашиваемый политический слой;
- дополнительно используются state-gap* элементы;
- итоговая визуализация зависит от комбинации исходной структуры SVG и runtime-изменений стилей.

3. Цель задачи

Перестроить архитектуру отображения провинций так, чтобы:
1. Исходный SVG не перекрашивался напрямую.
2. Политическая окраска рендерилась в отдельном overlay-слое поверх карты.
3. Zoom и pan больше не вызывали визуального рассинхрона между картой и цветом.
4. Существующие функции выбора, hover, режима игрока/мастера и выделения провинции продолжили работать.

4. Что нужно реализовать

4.1. Отказ от прямой перекраски исходных state*
Нужно убрать подход, при котором:
- основной путь провинции получает fill/stroke напрямую;
- state-gap* тоже перекрашивается динамически.

Исходные SVG-элементы провинций должны остаться:
- источником геометрии;
- объектом для hit detection;
- объектом для hover/click,

но не должны быть основным цветным слоем.

4.2. Ввести отдельный overlay для заливки провинций
Нужно создать отдельную SVG-группу, например:
- province-fill-overlay

В неё при каждом renderAll() / applyProvinceStyles() нужно рендерить отдельные визуальные элементы заливки провинций.

Рекомендуемый подход:
- для каждой провинции брать исходный SVG-элемент;
- делать cloneNode(true);
- удалять у клона id;
- запрещать клону pointer events;
- применять к клону нужный fill, fill-opacity, stroke для выделения;
- вставлять клон в overlay-слой.

То есть:
- оригинал остаётся интерактивной геометрией;
- клон становится цветной визуализацией.

4.3. Слой overlay должен находиться между картой и игровыми объектами
Порядок слоёв должен быть таким:
1. базовый SVG карты;
2. province-fill-overlay;
3. characters-overlay;
4. markers-overlay.

Это важно, чтобы:
- цвет провинций был виден;
- персонажи и маркеры не перекрывались цветным слоем;
- выбор и редактирование объектов оставались читаемыми.

4.4. Сохранить существующее поведение провинций
После переделки должны продолжить работать:
- hover по провинции;
- click по провинции;
- выбор провинции;
- выделение выбранной провинции;
- режим player/master;
- скрытие мастерских провинций в режиме игрока;
- изменение владельца провинции;
- обновление описания провинции.

4.5. Упростить или убрать зависимость от state-gap*
Если после перехода на overlay выяснится, что state-gap* больше не нужен для визуальной окраски, его нужно исключить из механики политического слоя.

Допускается один из вариантов:
- полностью перестать использовать state-gap* для окраски;
- оставить state-gap* только как декоративную часть исходной карты;
- использовать его только если он действительно нужен для специфического контура.

Но базовая реализация должна опираться на overlay поверх state*, а не на runtime-перекраску обоих слоёв.

5. Технические требования

5.1. Не ломать существующий zoom
Текущий zoom уже работает через viewBox, с ограничением min = 1, что соответствует базовой рамке просмотра.

Это поведение нужно сохранить:
- нельзя отдалять карту дальше стартового состояния;
- zoom in/out остаётся прежним;
- центрирование под курсором сохраняется.

5.2. Не ломать drag персонажей и маркеров
В проекте уже есть pointer-based drag для персонажей и маркеров через beginEntityDrag, handlePointerMove, endEntityDrag.

Новая реализация политического слоя не должна:
- перекрывать pointer events игровых объектов;
- мешать drag-and-drop;
- мешать выбору маркеров и персонажей.

У overlay-слоя провинций нужно явно отключить перехват событий, если это требуется:
clone.style.pointerEvents = "none";

5.3. Минимально затрагивать текущую архитектуру
Нужно по возможности не переписывать проект целиком.

Желательный объём изменений:
- заменить логику applyProvinceStyles();
- добавить/переиспользовать ensureOverlayLayer(id);
- убрать или перестать использовать getProvinceGapElement() и setProvinceVisualStyle() для политической окраски;
- не менять структуры JSON-данных.

6. Ожидаемый результат

После выполнения задачи должно быть следующее:

Визуально:
- цвет провинций выглядит стабильно при увеличении и уменьшении масштаба;
- не возникает ощущения, что цветной слой смещается отдельно от карты;
- выделение выбранной провинции читается;
- режим игрока/мастера визуально работает корректно.

Архитектурно:
- исходный SVG больше не используется как runtime-перекрашиваемый политический слой;
- политическая заливка вынесена в отдельный overlay;
- логика отображения карты стала более предсказуемой и расширяемой.

7. Критерии приёмки

Задача считается выполненной, если:
1. При zoom in/out цвет провинций остаётся визуально совмещённым с картой.
2. Исходные state* не перекрашиваются напрямую как основной политический слой.
3. Выбор провинции по клику работает.
4. Hover по провинции работает.
5. В режиме player скрытые провинции не показываются или отображаются в согласованном виде.
6. Персонажи и маркеры остаются поверх провинциальной заливки.
7. Drag персонажей и маркеров продолжает работать.
8. Не возникает новых артефактов слоя при renderAll().

8. Ограничения

Не нужно в рамках этой задачи:
- переделывать структуру JSON;
- реализовывать редактирование границ провинций;
- менять систему зума;
- менять систему редактора персонажей/маркеров;
- переписывать весь SVG вручную.

9. Предпочтительный план реализации

1. Проанализировать текущую реализацию applyProvinceStyles() и связанные функции.
2. Добавить/использовать ensureOverlayLayer("province-fill-overlay").
3. Реализовать функцию создания визуального клона провинции.
4. Перевести отрисовку цвета провинций на overlay.
5. Убрать прямую перекраску исходных SVG-элементов.
6. Проверить совместимость с hover, selection, player/master.
7. Проверить zoom + drag.
8. Закоммитить в develop.

10. Формат результата

Результат должен быть оформлен как:
- изменения в dnd-map-mvp/app.js;
- при необходимости небольшие изменения в styles.css;
- коммит в ветку develop с понятным сообщением.

Подходящее сообщение коммита:
Render province colors on overlay instead of base SVG
